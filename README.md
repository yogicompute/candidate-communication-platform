# Candidate Communication Platform

Recruiters manage candidates and send them SMS-style messages, individually or in bulk, and track each
message through Pending → Sent → Delivered → Read (or Failed), with safe retries for temporary failures.

- **Frontend:** Next.js 16 (App Router, TypeScript) + Material UI — `frontend/`
- **Backend:** Django 6 + Django REST Framework — `backend/`
- **Database:** SQLite locally, PostgreSQL in production
- **Messaging provider:** a local **simulation** (`backend/providers/dummy_server.py`), not a real SMS service

## Architecture

```
Browser ──▶ Next.js ──HTTP /api/v1──▶ Django API ──▶ provider adapter ──▶ dummy provider process
                                          ▲                                    │
                                          └──── signed status callbacks ◀──────┘
```

- `candidates/` — candidate CRUD, search, column filters, soft delete.
- `messaging/` — message attempts, status rules, idempotent send/bulk/retry, webhook processing.
- `providers/` — provider interface, dummy provider adapter, and the dummy provider server.

## Run locally

Prerequisites: Python 3.14 (3.12+ works), Node.js 22+.

**Backend** (terminal 1)
```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python manage.py migrate && python manage.py seed_candidates
python manage.py runserver 8000
```

**Dummy provider** (terminal 2)
```bash
cd backend && source .venv/bin/activate
python -m providers.dummy_server
```

**Frontend** (terminal 3)
```bash
cd frontend
npm install
cp .env.example .env.local
npm run dev
```

Open http://localhost:3000. Set `NEXT_PUBLIC_API_MODE=mock` in `frontend/.env.local` to run the UI without the backend.

## Simulating provider outcomes

The dummy provider decides by the **last digit** of the candidate's mobile number:

| Last digit | Outcome |
|---|---|
| 0–3 | Sent → Delivered → Read (plus a duplicate and an out-of-order callback, both ignored) |
| 4 | Sent → Delivered |
| 5 | Every other send: temporary delivery timeout (retryable) |
| 6 | Permanent failure: blocked by carrier |
| 7 | Every other send: rate limited (retryable) |
| 8 | Every other send: provider unavailable (retryable) |
| 9 | Permanent failure: invalid number |

Outage mode (every send fails as "temporarily unavailable"):
```bash
curl -X POST http://127.0.0.1:8100/control -H "Authorization: Bearer local-dummy-provider-key" \
  -H "Content-Type: application/json" -d '{"outage": true}'
```

## Deployment

**Backend + database → Render** (`render.yaml` blueprint). **Frontend → Vercel.**

On Render the dummy provider runs as a second process inside the API service (`backend/bin/start.sh`),
listening only on localhost; callbacks go to the API over localhost and are still HMAC-signed. This keeps
the free tier to one service and means the provider is never asleep when the API is awake.

### 1. Backend on Render
1. Push this repository to GitHub.
2. Render dashboard → **New → Blueprint** → select the repository. Render creates:
   - `ccp-db` (PostgreSQL, free)
   - `ccp-api` (web service, root `backend/`, health check `/api/v1/health/`)
3. When asked for `CORS_ALLOWED_ORIGINS`, enter your Vercel URL (e.g. `https://candidate-communication.vercel.app`).
   You can change it later under the service's **Environment** tab.
4. Wait for the deploy; open `https://<your-api>.onrender.com/api/v1/health/` → `{"status":"ok","database":"ok"}`.

Migrations and the demo candidates are applied automatically on every start.
Secrets (`DJANGO_SECRET_KEY`, `DUMMY_PROVIDER_API_KEY`, `PROVIDER_WEBHOOK_SECRET`) are generated by Render.

### 2. Frontend on Vercel
1. Vercel → **Add New → Project** → import the repository.
2. **Root Directory:** `frontend` (framework is detected as Next.js).
3. Environment variables:
   - `NEXT_PUBLIC_API_MODE` = `http`
   - `NEXT_PUBLIC_API_BASE_URL` = `https://<your-api>.onrender.com` (no trailing slash)
4. Deploy. If the Vercel URL differs from what you entered in Render, update `CORS_ALLOWED_ORIGINS` there.

### Environment variables (backend)

| Variable | Purpose |
|---|---|
| `DJANGO_DEBUG` | `false` in production |
| `DJANGO_SECRET_KEY` | Required when debug is off |
| `DATABASE_URL` | PostgreSQL connection string (set by Render) |
| `CORS_ALLOWED_ORIGINS` | Comma-separated frontend origins |
| `DUMMY_PROVIDER_API_KEY` / `PROVIDER_WEBHOOK_SECRET` | Shared by the API and the dummy provider |
| `PROVIDER_TIMEOUT_SECONDS` | Provider request timeout |

### Free-tier limits
- Render free web services sleep after ~15 minutes idle; the first request then takes ~50 s.
- Render free PostgreSQL databases expire after 30 days. Use a paid plan for anything long-lived.
- The dummy provider keeps pending callbacks in memory; a restart drops callbacks not yet delivered.

## Security notes
- There is **no authentication**: anyone with the URL can view, add, message and delete candidates.
  Add login (e.g. session or token auth) before using real data.
- Provider callbacks are verified with an HMAC-SHA256 signature over the raw body.
- CORS only allows the configured origins; errors never expose stack traces.
